EISOL Field Sync — User guide

EISOL Field Sync keeps HubSpot tickets, deals and companies in step with Jira issues, in both directions, and copies HubSpot notes and Jira comments between them. It runs entirely on Atlassian Forge.

See pricing.

Before you start

  • You need to be a Jira administrator to set the app up.
  • You need a HubSpot account, and a HubSpot user who may connect apps to it (a Super Admin, or a user with permission to install apps). The app works with HubSpot's free CRM and with paid editions. On the free CRM, which allows 10 custom properties in total, the Jira details need three of them for each type of record you sync (section 6).
  • One HubSpot account can be connected to one Jira site.

1. Connect HubSpot

  1. In Jira, go to Settings → Apps → EISOL Field Sync.
  2. Select Connect HubSpot. A HubSpot page opens.
  3. Choose the HubSpot account to connect, check the permissions the app asks for, and allow them. HubSpot may first warn that it has not reviewed the app yet; type the confirmation text it asks for and continue.
  4. The page that opens shows a confirmation code and the Jira site it is for. Return to the app's settings page on that site, enter the code under Enter the confirmation code within 10 minutes, and select Finish connecting. The settings page then shows the connected account.

Nothing is connected until the code is entered. The code ties the approval in HubSpot to an administrator of this Jira site, so a connection link that was forwarded, or sent to you by someone else, cannot connect an account by itself. If a colleague approves in HubSpot for you, ask them for the code on their page. Enter a code only on the settings page of the site named on that page, and never give a code to someone who asks for it.

The app asks HubSpot for permission to read and write tickets, deals and companies, to read their property definitions and create three properties of its own (see section 6), and to read the list of HubSpot users who own records.

2. Add a sync rule

A rule says which HubSpot records get a Jira issue, where the issue goes, and how the fields match. Select Add a rule.

  1. HubSpot records: tickets, deals or companies.
  2. Jira project and issue type for the new issues.
  3. Which records get an issue (tickets and deals): choose a pipeline, and optionally the stages. A record gets an issue when it is created, or when it reaches one of the chosen stages, after the rule is switched on. With no stages chosen, every stage counts, so an older record also gets an issue when it moves to another stage. Other records that existed before are not imported; you can link them by hand (section 5).
  4. Fields: the app suggests a starting set, for example ticket name to Summary, description to Description, priority to Priority, and ticket status to Status. For each row choose the HubSpot property, the Jira field, and the direction:
    • Both ways: a change on either side is copied to the other.
    • HubSpot → Jira or Jira → HubSpot: only changes on the first side are copied. A change on the other side stays where it is until the first side changes again.

The Jira field list shows only fields that can hold the HubSpot value: text with text, numbers with numbers, dates with dates (a HubSpot date-and-time such as a deal's close date can go to a Jira date), choices with choices, owners with users, and stages with statuses. Read-only HubSpot properties can only be copied to Jira. The list holds the fields Jira offers when an issue of that type is created. If a field such as Priority is missing, add it to the issue type in Jira first (in a team-managed project, under the project's settings, in the fields of that work type), and open the rule again.

  1. Values: for choices, owners and stages, select Values on the row to see how they pair up. There is one table for each direction, so you can, for example, send HubSpot "Urgent" to Jira "Highest" while sending Jira "Highest" and "High" both back as "High". The app fills in a starting point: priorities by meaning, stages by their place in the pipeline (first stage to "To Do", closed stages to "Done", the rest to "In Progress"), and owners by email address where Jira shows it. A value without a pair is not copied.
  2. Required in Jira: if the issue type needs fields that are not mapped, give a value to use for every new issue.
  3. Copy HubSpot notes and Jira comments: on by default (section 4).
  4. Switch Sync is on, and select Save. The app checks the rule against Jira and HubSpot and lists anything it cannot use.

You can add several rules, for example one for support tickets and one for won deals. When you add a field to a rule that already syncs records, the side that has a value is copied to the side that has none; where both have values, HubSpot's are kept. If you delete a rule, a new rule for the same object and Jira project takes over its records.

3. How the sync works

  • HubSpot → Jira: the app looks for changed HubSpot records every five minutes.
  • Jira → HubSpot: changes reach HubSpot within seconds.
  • When both sides change the same field before the sync sees either change, the app reads the change history of that field and copies the later edit. Unrelated record edits and comments do not decide the winner. If the history is unavailable, incomplete or ambiguous, or both edits have the same timestamp, both values are kept and the problem is listed. Long Jira histories are read over several rounds. To resolve a held conflict, inspect the field histories and choose a one-way direction in the rule, then restore both ways once the values agree. Once a write is waiting to be retried, its chosen direction is kept while both field values stay the same.
  • Edits within about a second of each other: a Jira change is copied as soon as Jira reports it. If someone changes the same field in HubSpot in the moment between the app reading the HubSpot record and writing the Jira value to it, the app does not see that edit and the Jira value replaces it. The replaced value stays in the HubSpot property's history. For fields that people often change on both sides, choose one direction in the rule.
  • Only fields in the rule are copied. Values that the other side cannot hold are skipped, and the skip is listed under Recent problems on the settings page. Text is copied as plain text with its paragraphs and line breaks, and text longer than the other side accepts is cut.
  • If Jira or HubSpot refuses a mapped record-field update (for example a status the workflow cannot reach), the app tries again on the following rounds, three tries in all, and lists the problem. After that it leaves the two sides as they are until a mapped value changes again. A refused note or comment copy waits for its original text to change. Temporary service or connection failures remain queued for retry; a large backlog can take several rounds to finish.
  • If Jira identifies a rejected optional field while creating an issue, the app retries without that field (up to four create attempts). Required or unverified fields are not removed. The issue stays linked, the omitted mapped value is retried, and the problem is listed. An ambiguous server or network failure is not immediately retried as another create.
  • If a linked HubSpot record cannot be read (404), the link and pending changes are kept. The app lists the problem once and retries when the record is accessible again; it does not assume deletion.
  • If a Jira issue cannot be read, its link is kept for retry: a 404 response can also mean missing access. Check permissions or unlink it deliberately if you want the sync to stop. A confirmed Jira deletion event removes the link.
  • Not synced in this version: attachments, contacts, custom objects, and records that existed before a rule was switched on (unless linked by hand).

4. Notes and comments

  • A HubSpot note on a synced record is copied to the issue as a comment, and a Jira comment on a synced issue is copied to the record as a note.
  • Each copy begins with a line saying where it came from, who wrote it and when.
  • Edits to the original are copied again. Edits to a copy stay on that side.
  • HubSpot notes are picked up as their records sync, including notes waiting for a new issue. Older note history is not imported in full. Jira comments created before linking, and comments written by apps or automation, are not copied. A note on several synced records is copied to one of their issues.
  • Copies in Jira are internal comments: on Jira Service Management issues they are not sent to customers. Jira comments restricted to a role or group are not copied.
  • Deleting a Jira comment deletes its HubSpot copy. If that request fails, it remains queued for retry without another deletion event. Deleting a HubSpot note does not change Jira in this version.
  • Missed comment events are checked by a background scan. Issues with many comments are read over several rounds; a busy backlog can delay those copies.
  • Formatting is kept where both products support it: paragraphs, line breaks, headings, lists, quotes, code, bold, italic, underline, strike-through and links.

5. The HubSpot panel in Jira

Open an issue and select HubSpot in the issue's side panel.

  • For a synced issue, the panel shows the HubSpot record, a link to it, and when it was last synced.
  • To link an existing record, choose a rule under Sync rule, enter the HubSpot record ID or paste the address of its page under HubSpot record ID or address, and choose under When the two differ which side's values to keep. Then select Link. The issue must be in the rule's project.
  • Unlink stops syncing the issue. The record keeps a mark, so the app does not make a new issue for it.

Only project administrators can link or unlink. A ticket or deal must be in the rule's pipeline; for a company rule, any company can be linked. The stage and age of the record are not checked for a manual link.

6. Jira details in HubSpot

The app adds three properties to synced records, in a group named Jira (EISOL Field Sync): Jira issue (the key), Jira status, and Jira link. They are kept up to date by the app. To see them on the record page, add them to the record's sidebar in HubSpot.

Existing accounts may still show the earlier group name Jira (EISOL HubSpot Sync) and earlier property descriptions. The app does not rename existing groups or properties automatically; their internal names are unchanged, so the sync continues to use them.

HubSpot's free tools allow 10 custom properties in total, so on the free CRM the app needs three free ones for each type of record it syncs. If HubSpot refuses them, the sync goes on without the Jira details, Recent problems says so, and the app tries again a day later. The same happens when the properties are archived in HubSpot: restore them there (Settings → Properties → Archived); the app looks again a day later and fills them as records sync.

7. Disconnecting

  • If a connection is refused, the app does not save its tokens. An app entry may still remain under HubSpot Connected Apps. Before removing it there, check that no other Jira site relies on the same app installation. Use only one Jira site per HubSpot account.
  • Change connection settings from one administrator session at a time. Overlapping disconnect, reconnect or reset operations can require connecting again; the app stops rather than send an older operation with a replacement account’s tokens.
  • Operations already sent with the old connection may still finish during disconnection. The app binds tokens to the account and connection time, and refuses to use a replacement account’s tokens for an older operation.
  • Disconnect (settings page) stops the sync, revokes this site's access to your HubSpot account, and deletes the app's tokens. Rules and links are kept, so connecting the same account again resumes the sync. To remove the app from HubSpot itself, uninstall it in HubSpot.
  • To stop using the app, select Disconnect before you uninstall it from Jira, and uninstall it in HubSpot as well. Uninstalling from Jira alone does not revoke the app's access to HubSpot; Atlassian deletes the app's stored data, tokens included, after its retention period.
  • To connect a different HubSpot account, select Disconnect and then Use another account, which makes the app forget its links. Issues and HubSpot records are not deleted. The rules are kept, switched off: check them against the new account (its pipelines, stages and owners) and switch them on again.
  • When you delete a synced Jira issue, the app clears the Jira details on the HubSpot record and does not make a new issue for it.

9. Data and privacy

The app runs on Atlassian Forge, and EISOL runs no servers for it. Synced content moves between Jira and HubSpot only. Rules that pair HubSpot owners with Jira users keep those users' Atlassian account IDs: the app reports them to Atlassian once a week and removes an account from the rules when Atlassian reports it as closed. See the privacy policy, the Data Processing Addendum and support and service levels.
